# Spike: reach SkyPilot from a JVM process

**THROWAWAY.** Answers issue #18 of map #1. Does not merge; the bridge decision (#19) cites it.

- `SkyRest.java` — the preferred arm: raw HTTP against the SkyPilot API server, JDK `HttpClient` only.
- `SkyCli.java` — the comparison arm: `sky` as a subprocess.
- `run.sh rest` / `run.sh cli` — one command each. Needs a JDK 25 and a reachable API server.

Run against SkyPilot **0.13.0** (`api_version` 56), API server on `127.0.0.1:46580`,
target `kubernetes/kind-skypilot` (kind under rootless podman) on 2026-08-08.

---

## What the spike could and could not reach

A real launch was submitted, scheduled, optimized and provisioned: the pod reached
`Pod is up.` Runtime setup then failed, because **pods on this host have no outbound TCP**
(rootless podman + kind: `nc -z 1.1.1.1 443` fails from a pod, succeeds from the node), so
SkyPilot's in-pod `uv pip install` could not reach PyPI.

So everything up to and including provisioning is **observed**; what a *running* job's
stdout streams like, and what job-level exit semantics look like, is **not tested here**.
That gap is host provisioning, not the bridge — it belongs to #21.

---

## Findings

### 1. The JDK's default HTTP client cannot mutate — and fails silently on reads first

`HttpClient` defaults to `HTTP_2`, attempting an h2c upgrade. SkyPilot's uvicorn rejects it:

```
400  Invalid HTTP request received.
```

That message is uvicorn's parser, not SkyPilot: no request id, no SkyPilot error, nothing
to retry on. **`GET`s still succeed under the same client** — so a Java client looks healthy
until its first mutation. `.version(HTTP_1_1)` must be pinned explicitly. Verified both ways.

### 2. The operation handle lives in a header the schema never mentions

Every mutation returns body `null` and puts the id in `x-skypilot-request-id`. The OpenAPI
declares neither. A client generated from `/openapi.json` receives `null` and has **no handle
on the operation it just started**.

### 3. Every call is asynchronous, including reads

`/status` is a POST that returns a request id; the result comes from polling
`/api/get?request_id=`. There is no synchronous read anywhere. Any Java client is a
request-id state machine, not a set of RPCs.

### 4. Failure uses a different transport *and* a different JSON shape — undeclared

A failed request answers **HTTP 500**, with the same `RequestPayload` nested one level
deeper under `detail`. The OpenAPI documents only the `200 → RequestPayload` case. The first
run of this spike treated 500 as retryable and burned a 10-minute timeout — a generated
client would throw and discard the payload that explains the failure.

### 5. Pickles: one kind is decodable, the other is not

This is the distinction that matters, and it is sharper than "results carry pickles":

| Field | Encoding | GLOBAL opcodes | Reachable from Java? |
|---|---|---|---|
| `error` | JSON `{"object": "<base64 pickle>"}` | **0** | Yes — a plain `dict` of `type`, `message`, `args`, `attributes`, `stacktrace`. A minimal pickle reader gets it. |
| `/status` → `handle` | base64 pickle | **5 STACK_GLOBAL** | No — real instances of `sky.backends.cloud_vm_ray_backend.CloudVmRayResourceHandle`, `sky.provision.common.ClusterInfo`. Undecodable without reimplementing SkyPilot's classes. |
| `entrypoint`, `request_body` | base64 pickle | — | Opaque; echoes of the caller, not needed by a caller. |

So the *failure reason* is recoverable from a JVM (awkwardly). The *cluster handle* is not.

Decoded error, for the record:

```
RuntimeError: Failed to run setup commands on an instance. (exit code 1).
  Error: ... Pod spike-jvm-9fc34560-head terminated: Error (exit code 1).
```

### 6. The OpenAPI is 118 routes of mostly-untyped surface

Generated by FastAPI, `openapi 3.1.0`, `title: FastAPI`, `version: 0.1.0` — it describes the
server's Python signatures, not a product contract. Every mutation route declares its 200 as
an **empty schema `{}`**. Only `/api/get` has a response model. Within `RequestPayload`,
`return_value` and `error` are typed `string` while actually holding JSON, base64 pickles, or
a bare integer depending on the call. Generation gets you request bodies and nothing else.

### 7. The task is an opaque YAML string

`LaunchBody.task` is typed `string`. A Java caller hand-builds SkyPilot task YAML and posts it
blind. There is no structured task type to bind to, so **no schema change is visible to a Java
compiler** — task-format drift across SkyPilot versions surfaces only at runtime. Encouragingly,
only `task` and `cluster_name` are required of `LaunchBody`'s 27 fields; the rest (`env_vars`,
`client_api_version`, `using_remote_api_server`, `file_mounts_blob_id`) are the Python client's
internal plumbing that a JVM would be impersonating.

### 8. Log streaming from a JVM works, but it is a terminal, not a feed

`GET /api/stream?request_id=…&follow=true&format=plain` is a held chunked `text/plain`
connection, read straight from `HttpResponse.BodyHandlers.ofInputStream()`. It genuinely
streams. But even at `format=plain` it carries **ANSI escapes** (`\e[32m`, `\e[2m`) and
box-drawing, and progress is written with carriage returns — the first "line" the spike read
was **4022 characters** of spinner rewrites. It is output for a human terminal that a backend
would have to de-ANSI and re-segment. There are no record boundaries and no timestamps.

### 9. Authentication is a deployment property, not a client one

The local server needs none. `/api/health` advertises `basic_auth_enabled`,
`service_account_token_enabled`, `ingress_basic_auth_enabled`, `external_proxy_auth_enabled`,
and the server exposes `/api/v1/auth/token`. Bearer tokens over standard HTTP headers are
nothing special from Java — this is the **least** problematic part of the surface.

### 10. What would exist twice

Concretely, from what the spike had to do by hand: task YAML construction and its validation;
interpretation of the request state machine; de-ANSI and re-segmentation of logs; and, on the
REST path specifically, any understanding of `handle` — cluster identity and the infra actually
chosen are reachable there **only** through Python objects. Note this last one is *not*
inherent: `sky status -o json` already returns those same facts as plain JSON (see the CLI
section), so it is a property of the REST surface, not of SkyPilot.

The optimizer's choice (the "Considered resources" table) arrives as a rendered table in the
log stream on both arms, never as data.

## The CLI arm, for comparison — and it inverts the expected result

See `cli-run.txt`. Same operations through `ProcessBuilder`.

**The surprise: the CLI's JSON is strictly better structured than REST's for reads.**
`sky status -o json` returns a flat JSON list of 35 named fields — `cloud`, `region`,
`accelerators`, `cpus`, `nodes`, `resources_str`, `status`, `cluster_hash`,
`cluster_name_on_cloud` — and contains **no base64 pickle at all**. The CLI decodes the very
`handle` that `/status` over REST hands back as an opaque `CloudVmRayResourceHandle`. The
supported-but-"human-oriented" surface exposes the infra actually chosen as data; the
richer-looking REST surface does not.

That flag is `-o/--output json`, and it exists on `status`, `jobs queue`, `api status` and
`cost-report` only. (`--format json` does **not** exist in 0.13.0 — the first version of this
spike assumed it and got `Error: No such option: --format`, exit 2.)

Against that, the CLI's costs are real:

- `launch`, `logs`, `check` and `down` have **no** machine-output mode — human text with ANSI,
  box-drawing and emoji, which the spike has to strip.
- A mutation's only structured result is its **exit code** (launch failed: exit 1).
- A task must be **materialised to a YAML file on disk** before launching — a filesystem
  coupling the REST arm does not have.
- Errors arrive as a rendered Python traceback line
  (`sky.exceptions.ClusterNotUpError: …`), to be recognised by string matching.

---

## What this spike does **not** decide

Whether the bridge is REST, a Python service, or the CLI is **#19's** call. This is evidence,
and the headline for that decision is the inversion in the CLI section: the REST surface is
reachable and does stream from a JVM, but it costs an undeclared header contract, an undeclared
failure shape, hand-built YAML and one genuinely opaque field — while the surface SkyPilot
actually documents hands back the same reads as clean JSON.

Untested here, and worth weighing before #19 closes: streaming a *running* job's stdout, and
job-level exit semantics. Both need a host where pods have egress (#21).
