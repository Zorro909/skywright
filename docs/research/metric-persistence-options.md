# Metric persistence options for a greenfield, spot-heavy setup

## Scope and the important distinction

This note surveys the homes named in issue #8 as of **2026-08-04**. It compares them; it does not select one.

`O2` has two independent requirements:

1. **Identity and step continuity:** a restarted process can append to the same logical run at the next intended step.
2. **Tail durability:** every metric that the application considers committed survives a network outage or destruction of the spot VM.

Most trackers provide the first. None, by itself, proves the second or makes model-checkpoint writes and metric writes atomic. A strict gap-free contract still needs an application protocol: retain the run ID and next step in the durable checkpoint, define whether a step is committed before or after its metrics, and either synchronously acknowledge those metrics or persist a replayable metric outbox outside the disposable VM. Otherwise a crash between “save checkpoint” and “log metric” produces either a hole or a duplicate.

The loss bounds below therefore separate:

- data already acknowledged by a remote service;
- data written only to a local SDK/event file;
- data still in a client queue;
- the model/checkpoint step from which training resumes.

## Evidence and implications by option

### W&B

- W&B says a lost internet connection causes continuous retry while the training program continues. Offline mode saves locally and `wandb sync` uploads later. The sync command explicitly handles **offline or incomplete** local runs. ([connection-loss support](https://docs.wandb.ai/fr/support/models/articles/what-happens-if-internet-connection-is-l), [`wandb sync`](https://docs.wandb.ai/models/ref/cli/wandb-sync))
- W&B SDK 0.24.1 release notes say all data is stored in the run's `.wandb` file and can be reuploaded. That gives a recovery path only while that file survives; no cited source claims the file is synchronously durable on an instance that is about to disappear. ([SDK 0.24.1 notes](https://docs.wandb.ai/release-notes/sdk-releases))
- `resume="must"` and `"allow"` reopen an existing ID at its last W&B step. `auto` requires the same filesystem; explicit IDs work across filesystems. ([resume guide](https://docs.wandb.ai/models/runs/resuming))
- Public API run filters and `scan_history()` provide both cross-run selection and complete, unsampled per-run history. ([import/export and Public API guide](https://docs.wandb.ai/models/track/public-api-guide))
- System metrics are automatically logged, and the reference covers CPU, memory, disk, network and accelerators. Application-domain values such as examples/sec and data-loader wait are not machine counters and should be logged explicitly. ([logging overview](https://docs.wandb.ai/models/track/log), [system metric reference](https://docs.wandb.ai/models/ref/python/experiments/system-metrics), [settings](https://docs.wandb.ai/models/ref/python/experiments/settings))
- TensorBoard integration saves relevant `tfevents` files, can launch an embedded TensorBoard view, and can sync event logs from S3/GCS/Azure. ([TensorBoard integration](https://docs.wandb.ai/models/integrations/tensorboard))
- Current public prices and storage quotas are from W&B's own pricing table. ([W&B pricing](https://wandb.ai/site/pricing/))

**Implication:** W&B has the most explicit combined network-outage, resume, query and TensorBoard story among the live hosted candidates. Its remaining `O2` gap is not tracker identity; it is the unsent local tail plus coordination with the training checkpoint.

### Neptune

- The current `Run` API says default mode is asynchronous background synchronization, the default log directory is `.neptune`, local metadata/logs use SQLite, network/queue callbacks exist, `close()` waits for queued data, and a supplied existing `run_id` resumes that run. ([Neptune `Run`](https://docs.neptune.ai/run))
- Offline mode stores metadata on local disk and requires manual synchronization; each SQLite file corresponds to a run. ([offline logging](https://docs.neptune.ai/offline))
- Metric steps must increase within a series. ([`log_metrics()`](https://docs.neptune.ai/run/log_metrics))
- Query APIs return filtered run tables and per-step metric DataFrames. ([runs query API](https://docs.neptune.ai/neptune-query/runs/), [query metrics](https://docs.neptune.ai/query_metrics))
- Neptune documents hardware monitoring through a utility script. ([hardware monitoring](https://docs.neptune.ai/hardware_monitoring))
- Most importantly for a greenfield decision in August 2026, Neptune says hosted SaaS and its API shut down on March 5, 2026, hosted data was deleted, and self-hosted image repositories were removed March 8. ([Neptune transition hub](https://docs.neptune.ai/transition_hub))

**Implication:** retain Neptune in the record because it was named by the ticket, but do not compare its old hosted feature set as if it can still be purchased.

### Comet

- Comet uses background upload for training. Its current SDK configuration documents 3 HTTP retries with exponential backoff before offline fallback. The fallback writes locally, uploads automatically if connectivity returns, and otherwise produces a ZIP for `comet upload`. ([resume guide](https://www.comet.com/docs/v2/guides/experiment-management/resume-experiment/), [SDK configuration](https://www.comet.com/docs/v2/guides/experiment-management/configure-sdk/), [offline fallback](https://www.comet.com/docs/v2/api-and-sdk/python-sdk/advanced/fallback-to-offline/))
- An existing experiment key reopens the logical experiment, and the same API exposes project queries. ([resume guide](https://www.comet.com/docs/v2/guides/experiment-management/resume-experiment/), [REST read endpoints](https://www.comet.com/docs/v2/api-and-sdk/rest-api/read-endpoints/))
- CPU/GPU/host collection and CPU, GPU, network and disk sampling intervals are SDK configuration. ([SDK configuration](https://www.comet.com/docs/v2/guides/experiment-management/configure-sdk/))
- Comet's standard TensorBoard integration ingests supported TensorBoard items. Separately logging the TensorBoard folder enables panels that copy selected logs to a TensorBoard server. ([TensorBoard integration](https://www.comet.com/docs/v2/integrations/third-party-tools/tensorboard/), [TensorBoard panels](https://www.comet.com/docs/v2/guides/comet-ui/experiment-management/visualizations/comet-panels/))
- Comet documents per-metric sampling after 15,000 values and separate Total Fidelity support. ([limits and performance](https://www.comet.com/docs/v2/guides/experiment-management/limits-and-performance/))
- Prices, training-hour limits and storage quotas are current vendor figures. ([Comet pricing](https://www.comet.com/site/pricing/))

**Implication:** Comet's automatic offline fallback is stronger than a pure in-memory retry loop, but it still lands on the disposable machine unless Skywright moves that directory to durable storage.

### MLflow

- `log_metric(s)` defaults to synchronous operation; asynchronous mode must be selected and returns a future. ([MLflow fluent API](https://mlflow.org/docs/latest/api_reference/python_api/mlflow.html))
- `start_run(run_id=...)` resumes the run, preserves its attributes, clears its end time and marks it running. ([MLflow fluent API](https://mlflow.org/docs/latest/api_reference/python_api/mlflow.html))
- MLflow exposes cross-run search and built-in system metrics. ([search runs](https://mlflow.org/docs/latest/ml/search/search-runs), [system metrics](https://mlflow.org/docs/latest/ml/tracking/system-metrics/))
- A production shared store consists of the tracking server, a SQL backend for run/metric metadata, and an artifact store such as S3. File-backed metadata is legacy/maintenance mode. DB upgrades can require downtime and must be backed up. ([architecture](https://mlflow.org/docs/latest/self-hosting/architecture/overview/), [backend store](https://mlflow.org/docs/latest/self-hosting/architecture/backend-store/), [artifact store](https://mlflow.org/docs/latest/self-hosting/architecture/artifact-store/))
- TensorFlow autologging uploads TensorBoard logs **on training end**. That is useful evidence that raw logs can be artifacts, but is not a crash-safe PyTorch upload strategy. ([MLflow TensorFlow API](https://mlflow.org/docs/latest/api_reference/python_api/mlflow.tensorflow.html))

**Implication:** synchronous MLflow metric calls provide the clearest application-visible acknowledgement boundary among the self-hosted choices. Availability and durability then depend on operating the server/database correctly.

### Aim

- Aim is an Apache-2.0, self-hosted tracker with a local repository and a remote tracking server. The current released PyPI package is 3.29.1; the official README documents programmatic metric queries and cross-run UI analysis. ([Aim 3.29.1 on PyPI](https://pypi.org/project/aim/3.29.1/), [Aim repository](https://github.com/aimhubio/aim), [CLI/server](https://aimstack.readthedocs.io/en/latest/refs/cli.html))
- A run hash reopens a run, and `force_resume` handles a stalled run. System tracking is configurable on the run. ([continue runs](https://aimstack.readthedocs.io/en/latest/using/manage_runs.html), [run configuration](https://aimstack.readthedocs.io/en/latest/using/configure_runs.html))
- Aim QL and the Metrics Explorer query, group and aggregate large run sets. ([query language](https://aimstack.readthedocs.io/en/latest/using/search.html), [explorers](https://aimstack.readthedocs.io/en/latest/ui/pages/explorers.html))
- `aim convert tensorboard` is a one-way import command in the documented interface. ([Aim CLI](https://aimstack.readthedocs.io/en/latest/refs/cli.html))

**Implication:** Aim offers a focused, relatively compact self-hosted tracker, but the primary docs do not establish the failure semantics needed to bound `O2` loss over a remote connection. That gap needs a fault-injection prototype before treating it as durable.

### ClearML

- ClearML exposes cached-report semantics directly: `Logger.flush(wait=True)` waits for all outstanding uploads and events. The documentation does not state that each preceding `report_scalar()` is durable before such a flush. ([Logger API](https://clear.ml/docs/latest/docs/references/sdk/logger/))
- Explicit Offline Mode captures a task in a local session and later imports it; imports can target `previous_task_id` with `iteration_offset`. ([offline mode](https://clear.ml/docs/latest/docs/guides/set_offline), [`Task` API](https://clear.ml/docs/latest/docs/references/sdk/task/))
- `continue_last_task` retains prior logs/artifacts and begins after the previous maximum iteration. ([Task SDK guide](https://clear.ml/docs/latest/docs/clearml_sdk/task_sdk/))
- `Task.init()` enables resource monitoring and ClearML automatically captures TensorBoard data into its Web UI. ([`Task` API](https://clear.ml/docs/latest/docs/references/sdk/task/), [TensorBoard integration](https://clear.ml/docs/latest/docs/integrations/tensorboard/))
- Hosted prices and quotas are public. ([ClearML pricing](https://clear.ml/pricing))
- The open-source server comprises web, API and file services and depends on MongoDB, Elasticsearch and Redis. ClearML's backup guide requires consistent backups across the file server, Elasticsearch and MongoDB. ([server](https://clear.ml/docs/latest/docs/deploying_clearml/clearml_server/), [server configuration](https://clear.ml/docs/latest/docs/deploying_clearml/clearml_server_config/), [backups](https://clear.ml/docs/latest/docs/deploying_clearml/enterprise_deploy/extra_configs/backups/))

**Implication:** ClearML is feature-rich and has explicit same-task/offline-import paths, but its self-hosted data plane is the largest operational commitment in this set.

### Plain TensorBoard events in object storage

- PyTorch documents asynchronous event writing with defaults `max_queue=10`, `flush_secs=120`, and `purge_step` for a crash/restart in the same logdir. `flush()` writes pending events to the filesystem. ([PyTorch `SummaryWriter`](https://docs.pytorch.org/docs/stable/tensorboard))
- S3 stores complete objects atomically; `PutObject` replaces a same-key object and does not partially update a normal object. This is why an event file should not be treated as a directly appendable object. ([S3 `PutObject`](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html), [S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html))
- TensorBoard's programmatic DataFrame API is explicitly experimental and its documented implementation targets TensorBoard.dev. It is not a substitute for an application run catalog/query service. ([TensorBoard DataFrame API](https://www.tensorflow.org/tensorboard/dataframe_api))

**Implication:** raw events maximize TensorBoard fidelity and minimize vendor/service cost, but they leave the difficult parts of `O2` and `O6` to Skywright. A robust form is not “write one live event file straight into S3”; it is an append-only sequence of sealed/immutable event segments plus a durable checkpoint/manifest protocol, or a service/mount whose durability has been tested.

## What SkyPilot provides

SkyPilot provides lifecycle and transport primitives, not a metric store:

- Managed jobs recover preemptions/hardware failures but restart from scratch unless the application writes and reloads checkpoints from persistent storage. ([managed jobs](https://docs.skypilot.co/en/latest/examples/spot-jobs.html))
- A bucket can be mounted for checkpoints. `MOUNT_CACHED` is explicitly asynchronously synchronized, so it must not be assumed to make the metric tail immediately durable. ([cloud buckets](https://docs.skypilot.co/en/latest/reference/storage.html))
- `$SKYPILOT_TASK_ID` remains stable for a task across recoveries and is therefore a useful external tracker run key. SkyPilot's own example passes it to W&B. ([managed jobs example](https://docs.skypilot.co/en/latest/examples/spot-jobs.html))
- The SkyPilot dashboard shows job status/duration/recovery count and logs, and can surface a W&B URL printed by the job. It does not expose training-metric persistence or cross-run metric queries. ([managed jobs dashboard](https://docs.skypilot.co/en/latest/examples/spot-jobs.html), [external links](https://docs.skypilot.co/en/latest/running-jobs/external-links.html))
- SkyPilot can expose a TensorBoard port on a long-lived cluster, but exposed ports are public unless separately secured and disappear with the cluster. That is access, not persistence. ([opening ports](https://docs.skypilot.co/en/latest/examples/ports.html))

## Findings that cut across every option

1. **No candidate alone proves strict gap-free `O2`.** W&B, Comet, MLflow, Aim and ClearML can append to the same logical run; Neptune's retained SDK could too. All still require a durable run ID, restored global step and a defined metric/checkpoint commit protocol.
2. **A local offline spool is not a spot-safe spool.** W&B, Neptune, Comet and ClearML all document useful local recovery paths. Those paths protect a network outage, not destruction of an ephemeral VM, unless the spool directory itself is placed on storage with tested synchronous durability.
3. **Exact online tail-loss bounds are generally undocumented.** W&B and Comet document retry/local recovery; Neptune documents local SQLite and callbacks; Aim and ClearML document much less about queue acknowledgement. None publishes a general “at most N metric points on `SIGKILL`/VM loss” guarantee. PyTorch event writing is the exception with visible queue/time defaults, but a later uploader adds another unbounded-by-default interval.
4. **Built-in system metrics do not complete `O4`.** Machine counters such as CPU, GPU, RAM, disk and network are broadly supported. Training throughput and data-loading wait are application semantics and must be emitted as custom metrics whichever store is used.
5. **TensorBoard compatibility has three meanings.** W&B can preserve and serve actual event files. Comet can do so when the TensorBoard folder is logged. MLflow can retain them as artifacts. Aim and ClearML primarily ingest them into their own models/UI. Only raw event storage is inherently the TensorBoard format.
6. **The greenfield comparison has six live options, not seven.** Hosted Neptune was retired before this research date.

## Could not establish from primary sources

- A vendor-backed maximum buffered-loss count/time for sudden VM destruction in W&B, Neptune, Comet, Aim or ClearML online mode.
- A durable client-side replay spool in MLflow asynchronous mode.
- A current supported path from Neptune 3.x stored metrics to a TensorBoard logdir.
- A reverse exporter that reconstructs complete TensorBoard event files from Aim or ClearML's native stored representation.
- Full AMD ROCm system-metric parity for every tracker. The relevant machine counters should be verified on Skywright's local AMD target; application metrics are unaffected.
- Transactional exactly-once coupling between a model checkpoint and metrics in any surveyed product.

Those unknowns are not minor implementation details for `O2`; any finalist whose documentation lacks a bound should be subjected to a kill-9, network-partition and VM-destruction prototype before an ADR treats the path as gap-free.
