# Local checkpoint seed acceptance and lineage

Research date: 2026-09-07. Sources are the accepted ADRs, current repository code and canonical GitHub issues. This note recommends an implementation; it does not change acceptance criteria.

## What must be preserved

ADR 0008 requires a new Run identity and Run Store, the identical Training Project Version, an exact seed checkpoint and a persisted predecessor relationship. Only the checkpoint is copied. A Transfer Worker resolves the predecessor's current Run Store location and owns copy/verify/publication outside the backend request's byte path and outside the Training Process. ADR 0016 resets a clone's Recovery Debt to zero. Project-specific restoration remains at `context.start()`. [ADR 0008](../adr/0008-address-run-stores-through-pre-registered-target-storages.md), [ADR 0016](../adr/0016-bound-infrastructure-recovery-with-progress-decayed-debt.md), [ADR 0020](../adr/0020-bind-one-run-context-to-each-training-process.md)

The owner's added #233 acceptance criteria require an actual production seeded/derived creation path, persisted lineage, a production reader and a test exercising accepted seeded creation through the backend contract. A fake fixture-only relationship does not satisfy this. #58 still owns complete clone inputs, source deletion/relocation and pruning races, repeated transfers, conflicting idempotency keys and Dataset Ordering Reset integration. [#233](https://github.com/Zorro909/skywright/issues/233), [#58](https://github.com/Zorro909/skywright/issues/58)

## Existing code stops short of seed ownership

`LocalRunRequest` has no seed fields. `ResolvedLocalRunAdmission` passes no `CheckpointSeedFacts` to the resolver and constructs `RuntimeMaterials` with a null `sourceCheckpoint`. `RunAcceptanceStore.accept` creates the Run UUID and calls admission inside its transaction, then persists the Run Record, current location and submission command. Thus there is no accepted seed creation path to expose merely by adding a reader. [Request](../../backend/src/main/java/de/zorro909/skywright/backend/runsubmission/LocalRunRequest.java), [admission](../../backend/src/main/java/de/zorro909/skywright/backend/runsubmission/ResolvedLocalRunAdmission.java), [acceptance store](../../backend/src/main/java/de/zorro909/skywright/backend/runsubmission/RunAcceptanceStore.java)

`RuntimeMaterials.SourceCheckpoint` already carries source Run UUID, exact reference and a source storage descriptor. The managed runtime converts that descriptor to a predecessor `TargetStorage` and its seed callback calls `RunStoreReader.read_exact` there. It does not copy the object into the child Run Store. [Materials](../../backend/src/main/java/de/zorro909/skywright/backend/runtimeassembly/RuntimeMaterials.java), [managed runtime](../../sdk/src/skywright/_managed_runtime.py)

`RunStoreRecorder.prepare_recovery` validates the external checkpoint's source Run, project version and reference, then records an external `RecoverySeed`. Until the child publishes its own checkpoint, subsequent recovery still needs that external snapshot. The existing `test_clone_recovery_preserves_external_seed_until_own_checkpoint` explicitly covers zero initial debt, debt on subsequent recovery and eventual independence after publication of a child checkpoint. It does not establish copied seed ownership. [Recorder](../../sdk/src/skywright/_run_store/implementation.py), [recovery tests](../../sdk/tests/unit/test_recovery.py)

Two details make a naive copy into the child's ordinary checkpoint directory incorrect:

- Checkpoint bytes include the originating `runId`. `read_exact` rejects a decoded checkpoint whose Run differs from its target. Preserving the exact checksum while changing that identity is impossible. The seed reader must distinguish the owner of the physical copy from the checkpoint's original Run identity. [Codec and reader](../../sdk/src/skywright/_run_store/implementation.py)
- Before the first attempt, recovery rejects any objects under the ordinary protocol prefix if its journal head is absent. `empty_store` currently lists the entire `<project>/<run>/v1/` prefix. A copied seed under that prefix needs an explicit, validated exception or a separate seed namespace under the stable Run inventory boundary. Do not create fake recovery history to bypass the guard. [Recovery journal](../../sdk/src/skywright/_run_store/recovery.py), [journal construction](../../sdk/src/skywright/_run_store/implementation.py)

The managed credential contract has only Dataset and child Run Store slots. A `RunStoreReader` for a different source storage still obtains the `run_store` credential slot. Supplying the source storage descriptor alone therefore neither grants correct access nor preserves role isolation. A child-owned seed allows execution to use only its existing Run Store projection. [Credential contract](../../sdk/src/skywright/credentials.py), [S3 client construction](../../sdk/src/skywright/_run_store/implementation.py)

## Reusable storage and worker code

`RunStoreAccess.resolveCheckpoint` validates an immutable reference and its metadata without reading checkpoint state. `stageDownload` already stages through a 1 MiB buffer, enforces maximum object size and available disk space, checks exact length and SHA-256, and returns a caller-owned temporary file. `VerifiedRunStoreObject.close` deletes it. The S3 adapter supports caller cancellation and request timeouts. These are suitable building blocks inside a Transfer Worker, although they do not implement destination multipart upload or a durable transfer operation. [Run Store access](../../backend/src/main/java/de/zorro909/skywright/backend/runstore/RunStoreAccess.java), [staged object](../../backend/src/main/java/de/zorro909/skywright/backend/runstore/VerifiedRunStoreObject.java), [S3 adapter](../../backend/src/main/java/de/zorro909/skywright/backend/runstore/S3RunStoreObjectStore.java), [operation control](../../backend/src/main/java/de/zorro909/skywright/backend/runstore/RunStoreOperationControl.java)

`BoundedS3Body` buffers the complete permitted body in memory. It is useful for small manifests, not large checkpoint payloads. The dataset verification worker instead demonstrates streaming SHA-256 and size verification with a 1 MiB buffer. [Bounded body](../../backend/src/main/java/de/zorro909/skywright/backend/runstore/BoundedS3Body.java), [verification worker](../../backend/src/main/java/de/zorro909/skywright/backend/datasetpublication/DatasetPublicationWorkerMain.java)

The existing Dataset Publication launcher establishes the production process pattern: a standalone Java worker, a non-secret job file, credentials delivered through stdin, a cleared child environment, durable projection lifecycle tracking and termination/cleanup. Its current work is verification and cleanup, not a generic S3-to-S3 seed transfer. Extract reusable worker execution/transfer code rather than implementing an unrelated third integrity protocol. Its `waitFor()` is unbounded, so a new bounded submission flow must supply its own operation deadline and terminate the worker on expiry. [Worker launcher](../../backend/src/main/java/de/zorro909/skywright/backend/datasetpublication/DatasetPublicationWorkerLauncher.java), [worker main](../../backend/src/main/java/de/zorro909/skywright/backend/datasetpublication/DatasetPublicationWorkerMain.java)

`S3DatasetCopyStorage` uses same-endpoint `CopyObject` for replacement staging. That is not a portable cross-endpoint checkpoint transfer. ADR 0008's floor requires multipart upload and ranged reads, but does not require server-side copy. [Dataset copy adapter](../../backend/src/main/java/de/zorro909/skywright/backend/datasetcatalog/S3DatasetCopyStorage.java), [ADR 0008](../adr/0008-address-run-stores-through-pre-registered-target-storages.md)

Target Storage registrations already support `transfer-worker` bindings. `VaultRoleAccess` permits backend and transfer-worker projections and explicitly refuses borrowing Training Process identities. `TargetStorageResolver.resolveRunOutput` accepts a consuming role, but resolves the active registration descriptor. `resolveRunOutputRead` honors a pinned/current location descriptor but hardcodes the backend role. A transfer needs the latter location semantics with transfer-worker credentials for both source and destination. Resolve the source descriptor through `RunAcceptanceStore.currentStorage`, not its immutable execution definition. [Resolver](../../backend/src/main/java/de/zorro909/skywright/backend/targetstorage/TargetStorageResolver.java), [Vault access](../../backend/src/main/java/de/zorro909/skywright/backend/credential/VaultRoleAccess.java), [current location](../../backend/src/main/java/de/zorro909/skywright/backend/runsubmission/RunAcceptanceStore.java)

## Smallest compliant implementation

These are recommendations inferred from the sources above.

1. Add an explicit local checkpoint seed request carrying predecessor Run UUID and exact checkpoint reference. Bind it into the canonical request digest. Persist lineage as Skywright-originated metadata in the same acceptance transaction as the child Run. Record affirmative root lineage for newly accepted unseeded Runs; legacy absence or reader failure remains unavailable.
2. Start with a deliberately narrow seeded request using the same published Project Version, Dataset and resolved configuration as the predecessor. The full editable clone flow remains in #58/#84. Pass real `CheckpointSeedFacts` into `RunDefinitionResolver`; never claim compatibility by setting its boolean without enforcing the corresponding rule. The resolver already rejects changed project version, ordering seed/policy and changed Dataset without Ordering Reset. [Resolver compatibility checks](../../backend/src/main/java/de/zorro909/skywright/backend/rundefinition/RunDefinitionResolver.java)
3. Allocate stable seed-preparation identity and child Run identity before external transfer side effects. A bounded, retryable preparation operation must preserve ownership through HTTP disconnect, duplicate requests and transaction failure. The current random UUID allocation inside `accept` is insufficient on its own for replaying pre-acceptance copies. This preparation is transfer work, not an offline compute submission queue.
4. A backend-hosted Transfer Worker resolves current source storage, stages and verifies the exact bytes, uploads one immutable child-owned seed object, verifies the destination and publishes a small completion receipt. Dispatch and accepted seed ownership require that receipt. Preserve the original checkpoint bytes and provenance. Never delete the predecessor object as part of seeding. Bound concurrency, operation time, staging disk, multipart parts and abandoned-upload cleanup.
5. Add a versioned seed namespace inside the child's stable inventory prefix, distinct from normal child checkpoints. Add a narrow Skywright SDK seed reader that derives its physical key from the accepted child and exact seed identity, verifies bytes with existing safe decoding and checks the decoded predecessor identity. Preserve the existing external-seed recovery semantics and zero initial debt, while reading the child-owned copy on every recovery until an ordinary child checkpoint exists. Explicitly handle the journal's initial empty-store guard. Do not loosen arbitrary key or wrong-Run checks on ordinary checkpoint reads.
6. Read lineage solely from the accepted relationship and verified seed receipt. Expose predecessor navigation, exact reference and seed ownership status independently of SkyPilot and other detail capabilities. Test real backend acceptance plus rendering, then execute the installed managed runtime after removing access to the predecessor object. Include corrupt transfer, lost response/replay, conflicting request identity and a first recovery before any child checkpoint.

Source disappearance before a verified owned copy must reject or leave preparation explicitly incomplete. It cannot produce an accepted seed that still depends on a prunable predecessor object. Current SDK pruning protects only configured retention selections and the final checkpoint; it has no cross-Run seed-transfer pin. Full source pruning, deletion and relocation coordination remains work that #58 explicitly requires. A terminal-source-only first slice reduces concurrent training/pruning exposure but does not replace deletion/transfer coordination. [Pruning](../../sdk/src/skywright/_run_store/implementation.py), [#58](https://github.com/Zorro909/skywright/issues/58)

No SkyPilot server or client SDK modification is needed. The required runtime changes belong to Skywright's own SDK. The owner has already approved adding the production creation/read lineage path to #233. An implementation satisfying the above does not require replacing a canonical acceptance criterion. If the desired shortcut is instead predecessor reads during training, bytes copied in a controller request thread, or lineage without a verified owned seed, that conflicts with ADR 0008 and needs an explicit owner decision before implementation.
